===============================================================================
WHY FALLBACKS -- READ THIS EVEN IF YOU SKIP THE REST
===============================================================================

`providers.resolve_role_candidates` reads a `fallbacks` list per role, and
`llm_quality.complete_validated_json` walks those candidates when the primary
fails to validate or the endpoint errors. Without it, ONE transient 503 in one
of nine stages kills the whole turn -- which is exactly what happened here:

    turn 35  FAILED  perception: all providers failed (last provider error: HTTP 503)

The endpoint was not down. A follow-up probe of that same model returned 8/8
with a 3.15s median. It was a blip, and a blip should cost a retry, not a beat.
Choosing a slower "sturdier" model to avoid this would have been the wrong fix:
it pays a permanent latency tax to insure against something a fallback handles
for free.

===============================================================================
REJECTED, AND WHY
===============================================================================

FASTEST DECODER IN THE CATALOGUE, UNUSABLE.
  meta-llama/llama-3.2-3b-instruct streams at 374.6 tok/s -- the highest number
  measured -- and scored 0/2 on schema. qwen/qwen3.5-9b: 294.5 tok/s, 0/2. Every
  stage here demands parseable JSON, so a schema miss costs a repair pass and
  the fastest decoder finishes last. Tokens per second is the wrong metric and
  it is the one every leaderboard reports.

THINKS WHEN YOU DID NOT ASK IT TO.
  zai-org/glm-4.7-flash: 1.75s short, 34.16s long, an effective 13.7 tok/s.
  Never use a `:thinking` variant for mapping, perception, utility or
  background_react; those roles emit small structured objects and reasoning
  tokens there are pure latency.

RIGHT SPEED, WRONG DOMAIN.
  holo3-35b-a3b was the fastest schema-valid model on the short call. It is
  H Company's computer-use vision-language model, fine-tuned from
  Qwen3.5-35B-A3B for GUI agent work and benchmarked on OSWorld. Rejected on
  capability AFTER the speed test had already picked it -- which is the reason
  to read the model card and not just the number.

A NEWER REVISION IS NOT A SAFE ASSUMPTION.
  qwen3.5-35b-a3b: 7.58s, 0/2 schema.  Qwen3.6-35B-A3B: 1.69s, 2/2, 270.8 tok/s.
  Same parameter count, same active experts, one revision apart, 4.5x latency
  and the difference between working and not. Check both directions.

PASSED THE TOY TEST, FAILED THE JOB.
  Qwen3.6-35B-A3B was first assigned `director` on the strength of a 2/2 score
  against a three-key JSON object, and then failed the real director_interpret
  contract three times on the first live turn -- 56s + 23s + 23s = 102 seconds
  to produce nothing, on chat 60. That is what produced tools/contract_bench.py
  and Stage 2 above. It passes the real contract comfortably on an ordinary
  scene; chat 60 is a pathological one (an enclosed character at 0.05 scale),
  which is precisely the case a fallback exists for.

===============================================================================
METHOD NOTES -- MISTAKES MADE, SO THEY ARE NOT REPEATED
===============================================================================

* DO NOT BENCHMARK TWO THINGS AT ONCE. Running the availability probe and the
  character contract test concurrently produced a wall of 429s that read as
  model unreliability and was entirely self-inflicted: the rate limit is on the
  ACCOUNT, shared across every model. gemma-4-26b-a4b-it's 3/8 availability
  score and four models' 0/2 character scores are contaminated by this and
  should be re-measured sequentially before being believed.
* A toy schema proves only that a model emits JSON. Use contract_bench.py,
  which sends the engine's own prompt and runs the engine's own validator.
* Measure with turn_bench.py, not by feel: it copies the database first, drives
  the real pipeline, and reads the engine's own llm_call log, so retries and
  repair passes are counted where they actually land.
* Re-run before trusting this file after a catalogue change. nano-gpt's
  included list moves, and two models here changed behaviour across a single
  revision.

===============================================================================
EMBEDDINGS STAY ON OPENROUTER -- DO NOT MOVE THEM
===============================================================================

  * nano-gpt's chat catalogue contains no embedding models at all.
  * All 6,480 stored memory vectors were embedded with pplx-embed-v1-4b.
    memory.py compares `embedding_model` per row and scores any row from a
    different model 0.0 on BOTH vector rankings. Switching does not "re-embed
    later" -- it silently drops the entire existing bank to keyword-and-exact
    match while new rows get all four signals. The bank splits into two eras
    and nothing says a word except one `_warn_stranded_embeddings` log line.
