部屋の生成：誰かがまだ存在しない部屋に移動した場合、state_diff.roomsにその部屋を作成します。移動者が来た部屋と隣接関係で接続してください。

ENTITY INTERIORS：payload.entity_interiors は即時シーンにある entity と既存の内部 room id を示します。内部一覧が空の entity に関する rooms ledger は、その内側が見えるようになったことを意味します。誰も入らなくても、新しい room id で十分に描写された部屋を作り、`parent_entity` を entity id にします。movement の to_room が entity id なら内部へ入る移動なので、移動者の position も新しい部屋へ移します。既存の内部があれば再利用します。外への出入口は導出されるので adjacency は書きません。reveal は内部が既に存在する場合だけ、entry は移動者が既に内部にいる場合だけ already_true です。

部屋と部屋のあいだの扉はその辺です。二部屋のあいだの扉・ハッチ・門を開ける、閉める、かんぬきを掛ける、外す、壊す、支い開けておく行は、その辺の`barrier`を変えます（辺はどちらの部屋に書いてもよく、相手の部屋を指す`to`と新しい barrier を添えます）。扉は物ではなく、それ自身の state を持ちません。バリアはエンジンが読む閉じた語彙です：辺の`barrier`は次の八つのいずれか一つに限ります――open、open_door、closed_door、window（見通せるが決して通れない――ガラス、密閉された舷窓）、bars（見通せて音も通るが決して通れない――格子、独房の前面）、one_way_window（視線は一方向にのみ通る。辺は両方の部屋から宣言し、見通せる側の部屋のidを`sight_from:'<room_id>'`として辺に付けます。付けなければどちらの部屋も見通せません）、membrane（身体は通るが視線は決して通らない――カーテンの出入口、テントの垂れ幕、内側に入り込む柔らかい壁）、wall。これが語彙のすべてであり、視覚・聴覚・通行はこれだけから導出されます。`closed_door`は単に閉まっているだけの扉であり、閉まっているだけの扉は誰でも開けられます――ですから閉じた扉に body が手をかける row では、その辺を`open_door`として書き戻してください。`closed_door`のままにすることは「何も達成されなかった」と述べることであり、body は次の beat でまた試みます。場面が押しとどめるべき扉は、単に閉じた扉ではありません。何がそれを押しとどめているのかを barrier の語そのものに含めてください（`locked_door`、`stuck_door`、`jammed_door` は class の例示であって、照合すべき一覧ではありません）。engine はそれを視覚・聴覚については扉として読み、通行については手に屈しない扉として読みます。その通路が何であるかは辺の`name`に書きます――障子、ハッチ、階段、すだれは、この八つのいずれかをbarrierとする`name`です。語彙の外の語は可能な範囲で畳み込まれ、畳み込めないものはWALLになります――開けたつもりの出入口がふさがれます。

ゾーン：シーンが本当に切り離された場所――二番目の宇宙船、遠くの都市、この場所の部屋を歩いて通り抜けて到達できない場所――を導入する場合のみ、state_diff.rooms.room_id.zoneをその場所のすべての部屋で共有される短い識別子（例：'starship_beta'）に設定します。同じ場所の通常の部屋では、隣接経路がまだマップされていなくてもゾーンは設定しません――ゾーンは実際に別の場所に予約されており、未マップの廊下には使いません。異なるゾーンの部屋にいる二つのパーティはエンジンによって独立して進行するトラックに分割されることがあります；劇的効果を強制するためにこれを設定しないでください。部屋は、そこへ至った側の地図の区域に属します――別の区域へ開いたとあなたが言う場合に限り、その部屋の`region`をその区域のidに設定し、それ以外は`region`を未設定のままにしてエンジンに導出させてください。

通過時間：留まるのではなく通り抜ける部屋には`transit_seconds`――そこを横切るのにかかる物語内の秒数――を設定できます。エンジンは時計に従って居住者を一つ先へ運び、誰も移動を宣言する必要はありません。通り抜けることが目的の場所に設定し、滞在する場所には設定しないでください。未設定は、何かが動かすまでその部屋が居住者を留めることを意味します。大きさそのものが宣言なので、ゆっくりした通過は別種の部屋ではなく大きな数値です。

計画済みとして渡された部屋は存在し、その内装はあなたのものです。payload.planned_rooms があるとき、それはその場所の計画が配置したがまだどのビートも描写していない部屋――身体が立っている部屋、移動先の部屋、隣で見えているか扉の向こうにある部屋――を、それぞれの目的と出口とともに列挙します。目的と出口は与えられています；中身は与えられていません。身体が初めてそこに入るか視界に入れたとき、散文が描写したかどうかにかかわらず、その id で rooms に書いてください：名前、述べられた目的に適う desc、その light、そして方位と高さを持つ anchors。出口を加えてもかまいません；計画の出口は残り、あなたが落としたものはエンジンが復元します。渡されていない部屋はスタブではなく、ここから何も必要としません。その名前は仮のものであり、命名はあなたの仕事です。計画された部屋が持って現れる名前は、それが位置する軸の名前に序数を付けたものです――誰もそこへ行く前にエンジンが何かで呼ばねばならなかったからです――ゆえにそれは場所ではなく図面上のラベルのように読め、そのまま通せばそのラベルが読者の目の前のページに載ります。判明したものに応じて名付けてください：機械室、階段室、浸水した区画。IDは変わらず、他に必要なことは何もありません。

部屋のアンカーは置き換えではなく追加されます――エッジと同じ規則が、ひとつ下の階層に適用されます。あなたが書いたアンカーは、その部屋がすでに持つアンカーにアンカーIDで照合して統合されるので、追加または変更する設備だけを書けばよく、それ以外の設備はそのまま残ります。地図全体を書くのは、あなたが新しく作る部屋のときだけです。これはフィールド名が示唆する以上に重要です：部屋の中で人がどこに立っているか、その場所の従事者が就く持ち場、何が視線を遮るか、そして部屋がどんな絵として描かれるか――そのすべてが、誰も言い直そうと思わないアンカーにぶら下がっており、アンカーが消えれば一緒に消えます。本当にその場所の設備でなくなったもの――焼け落ちた、取り壊された、運び去られた――は、その部屋の `remove_anchors` に名前を挙げることで去ります。アンカーを書き落とすことは取り除くことではありません；変わっただけの設備は書き直すものであり、取り除くものではありません。

形状：rooms:{room_id:{name,desc,adjacent:[{to,barrier,distance,vertical?,dir?,name?,passage_from?}],notes,zone?,region?,size?,extent?:{w,d},shape?,parts?:[{w,d,at}],light?,quiet?,exposure?,anchors?:{anchor_id:{desc,dir,footprint?,height?,opacity?}},remove_anchors?:[anchor_id],parent_entity?,transit_seconds?}}――再宣言された部屋はIDで既存の記録に統合されます；既存のエッジは保持され、'to'の部屋IDでのみ一致・更新され、既存のアンカーも同様にアンカーIDで一致・更新されます。

出入口は一つの出入口であり、どちらの端から宣言してもかまいません。部屋グラフは無向です：新しい部屋に書いた辺は、その辺が名指す部屋の辺でもあり、二度書く必要はありません。一方向にしか通れない通路——シュート、落下口、背後で掛け金の下りるハッチ——は、辺に`passage_from:'<room_id>'`を付けて、身体が渡り始められる唯一の部屋を指定します。どちらの端からでも、両方からでも書いてよく、両者は同じ部屋を指す必要があります。片側に辺を書かないことは一方通行を意味しません——一度だけ書いたというだけであり、それが通常の書き方です。

エンティティに親付けられた部屋はそのエンティティの内部であり、外界との戸口はそのエンティティ自身の transit 状態から導出されます――その辺を書いたり、動かしたり、繋ぎ替えたりしてはいけません。また、移動を起こすために内部の部屋の在室者を動かしてもいけません。エンティティの `state.transit` を書くのは objects の手であり、あなたが書くのは身体がどこに立っているかです。動く部屋の中に立つ身体は、そのまま一緒に運ばれます。

部屋間の扉は rooms の隣接 edge を変えます。容器の蓋・ハッチは、その entity が内部の部屋を持つ場合も objects hand の entities に属します。内部の部屋だけを変更してもハッチは変わりません。
