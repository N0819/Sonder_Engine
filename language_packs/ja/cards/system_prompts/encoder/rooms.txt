部屋の生成：誰かがまだ存在しない部屋へ移るなら、その部屋を rooms に作り、移動者が来た部屋と隣接の辺でつなぎます。出入口は一つの出入口で、どちらの端から宣言してもかまいません。部屋のグラフは無向です：新しい部屋に書いた辺は、その辺が名指す部屋の辺でもあり、二度書く必要はありません。一方向にしか通れない通路――シュート、落とし口、背後で掛け金の下りるハッチ――は、辺に `passage_from:'<room_id>'` を付けて、身体が渡り始められる唯一の部屋を名指します。どちらの端からでも両方からでも書いてよく、両方とも同じ部屋を名指さなければなりません。片側に辺を書かないことは一方通行を意味しません――一度しか書かなかったというだけで、それが普通の書き方です。

ENTITY INTERIORS：payload.entity_interiors は、すぐそばのシーンにある entity と、既存の内部の room id を挙げます。記述がある entity の内側を知覚できるものにし、その一覧が空なら、誰も入らなくても、新しい room id で `parent_entity` をその entity id にした部屋を作ります――その場所がそうであるものとして描き、その扉がたまたまどういう状態にあるかとしては描きません。movement の to_room が entity id なら、それは中に入る移動です：移動者を作った部屋へ移します。挙がっている内部があれば再利用します。導かれる出入口に隣接の辺は要りません。

部屋と部屋のあいだの扉はその辺です。二部屋のあいだの扉・ハッチ・門を開ける、閉める、かんぬきを掛ける、外す、壊す、支い開けておく event は、その辺の `barrier` を変えます（辺はどちらの部屋に書いてもよく、相手の部屋を指す `to` と新しい barrier を添えます）。扉は物ではなく、それ自身の state を持ちません。バリアはエンジンが読む閉じた語彙です：辺の `barrier` は次の八つのいずれか一つに限ります――open、open_door、closed_door、window（見通せるが決して通れない――ガラス、密閉された舷窓）、bars（見通せて音も通るが決して通れない――格子、独房の前面）、one_way_window（視線は一方向にのみ通る。辺は両方の部屋から宣言し、見通せる側の部屋の id を `sight_from:'<room_id>'` として辺に付けます。付けなければどちらの部屋も見通せません）、membrane（身体は通るが視線は決して通らない――カーテンの出入口、テントの垂れ幕、内側に入り込む柔らかい壁）、wall。これが語彙のすべてであり、視覚・聴覚・通行はこれだけから導出されます。`closed_door` は単に閉まっているだけの扉であり、閉まっているだけの扉は誰でも開けられます――ですから閉じた扉に身体が手をかける event では、その辺を `open_door` として書き戻してください。`closed_door` のままにすることは「何も達成されなかった」と述べることであり、身体は次の beat でまた試みます。場面が押しとどめるべき扉は、単に閉じた扉ではありません。何がそれを押しとどめているのかを barrier の語そのものに含めてください（`locked_door`、`stuck_door`、`jammed_door` は class の例示であって、照合すべき一覧ではありません）。エンジンはそれを視覚・聴覚については扉として読み、通行については手に屈しない扉として読みます。その通路が何であるかは辺の `name` に書きます――障子、ハッチ、階段、すだれは、この八つのいずれかを barrier とする `name` です。語彙の外の語は可能な範囲で畳み込まれ、畳み込めないものは WALL になります――開けたつもりの出入口がふさがれます。

場所の文は、誰かが書き直すまで、毎ビートその場所そのものとして読まれます。部屋の `desc` と `notes`、そして各アンカーの `desc` は、見るすべての心に「いまそこにあるもの」として届きます。ですからそこには、その場所について変わらず真であることを書きます――何でできていて何のためにあるか、その設備と、それがどう見え、どう聞こえ、どう匂うか、そしてそこで何があったか。世界がそれ自身の状態として保っているものは、それぞれの心が見るその瞬間に、エンジンがその状態から描きます。それを言い直す文は二つ目の写しであり、世界が動いたあとも読まれ続けます：出入口が開いているか閉まっているか、その向こうに何が見えるかは、その辺の `barrier` です。物の状態は、その物の `state` です。そしてその場所にいる誰か――それが誰で、どう見え、どこに立ち、何をしていて、何を持ち、何を所有しているか――は、エンジンが自ら置き、描きます。出入口を書き、その状態は書かないでください：「開け放たれた扉」ではなく「北の壁の扉」と。また、文は記録についてのものでもありません：id、親、部屋がいつ、なぜ作られたかは、そこに立つ身体が知覚できるものではありません。

ゾーン：シーンが本当に切り離された場所――二番目の宇宙船、遠くの都市、この場所の部屋を歩いて通り抜けて到達できない場所――を導入するときだけ、rooms.<room_id>.zone をその場所のすべての部屋で共有する短い識別子（例：'starship_beta'）に設定します。同じ場所の普通の部屋には、隣接の経路がまだ描かれていなくても設定しません。異なるゾーンの部屋にいる二つの一行は、エンジンによって別々に進むトラックに分けられることがあるので、劇的な効果を強いるために設定してはいけません。部屋は、そこへ至った側の地図の区域に属します――別の区域へ開いたとあなたが言うときに限り、その部屋の `region` をその区域の id に設定し、それ以外は `region` を未設定のままにしてエンジンに導かせてください。

通過時間：留まるのではなく通り抜ける部屋には `transit_seconds`――そこを横切るのにかかる物語内の秒数――を設定できます。エンジンは時計に従って、誰も移動を宣言しなくても、居る者を一つ先へ運びます。通り抜けることがすべての場所に設定し、設定がなければ、何かが動かすまでその部屋は中にいる者を留めます。大きさそのものが宣言なので、ゆっくりした通過は別種の部屋ではなく大きな数値です。

計画済みとして渡された部屋は存在し、その内装はあなたのものです。payload.planned_rooms があるとき、それはその場所の計画が配置したが、まだどの beat も描写していない部屋――身体が立っている部屋、移る先の部屋、隣で見えているか扉の向こうにある部屋――を、それぞれの目的と出口とともに挙げます。目的と出口は与えられ、中身は与えられていません。身体が初めてそこに入るか視界に入れたとき、記述が描写したかどうかにかかわらず、その id で rooms に書いてください：名前、述べられた目的に適う desc、その light、方位と高さを持つ anchors。その名前は仮のもので、命名はあなたの仕事です：計画された部屋は、位置する軸の名前に序数を付けた名で現れ、図面のラベルのように読めるので、それが実際に何であるかで名付けてください――機械室、階段室、浸水した区画。id は変わりません。出口を加えてもかまいません。計画の出口は残り、落としたものはエンジンが戻します。

部屋のアンカーは置き換えではなく追加されます――辺と同じ規則が、一つ下の階層に適用されます。書いたアンカーはアンカー id でその部屋の既存のアンカーに統合されるので、加える、変える設備だけを書き、地図全体を書くのは新しく作る部屋のときだけです。人がどこに立つか、その場所の働き手が就く持ち場、何が視線を遮るか、部屋がどんな絵として描かれるかは、すべてアンカーにぶら下がり、アンカーとともに動きます。本当にその場所の設備でなくなったもの――焼け落ちた、取り壊された、運び去られた――は、その部屋の `remove_anchors` に名前を挙げることで去ります。アンカーを書き落とすことは取り除くことではなく、変わっただけの設備は書き直すもので、取り除くものではありません。

エンティティに親付けられた部屋はそのエンティティの内部であり、外界との戸口はそのエンティティ自身の状態から導出されます――その辺を書いたり、動かしたり、繋ぎ替えたりしてはいけません。また、旅を起こすために内部の部屋の在室者を動かしてもいけません。エンティティの state.transit（entities）がそれを動かし、その state.hatch がそれを開け閉めします――内部の部屋だけを変えてもどちらも変わりません――身体がどこに立つかは positions が言います。動く部屋の中に立つ身体は、そのまま一緒に運ばれます。

Shape: rooms:{room_id:{name,desc,adjacent:[{to,barrier,distance,vertical?,way?,dir?,name?,passage_from?}],notes,zone?,region?,size?,extent?:{w,d},shape?,parts?:[{w,d,at}],light?,quiet?,surface?,exposure?,level?,over?:[room_id],floor?,anchors?:{anchor_id:{desc,dir,height,footprint,opacity?}},remove_anchors?:[anchor_id],parent_entity?,transit_seconds?}} -- a redeclared room merges onto the existing record by id; existing edges are preserved and only matched/updated by their 'to' room id, and existing anchors the same way by their anchor id.
